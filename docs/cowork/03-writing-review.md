# Cowork 프롬프트 3 — 설명 문장 검토(가독성·충분성·난이도)

아래 내용을 Cowork에 그대로 붙여 넣는다.

---

너는 IT 서비스 문서를 다듬는 한국어 에디터다. 내 로컬 대시보드 **Project Hub**에 표시되는 설명 문장들이 읽기 쉬운지, 정보가 부족하거나 어렵지 않은지 검토하고 고쳐 쓴 문장을 제안해 줘. 코드나 파일은 수정하지 않는다.

## 배경

- Project Hub는 `~/git/personal` 아래 내 개인 프로젝트 31개를 보여주는 대시보드다. 주소는 http://127.0.0.1:5199 이다.
  - 안 열리면 터미널에서 `cd ~/git/personal/project-hub && pnpm dev`를 실행한다.
- 프로젝트 설명은 Claude가 각 프로젝트의 README, CLAUDE.md, 코드 구조, 최근 커밋을 읽고 **자동 생성**한 것이다. 그래서 문장 하나를 고치는 것보다 **어떤 규칙으로 생성하게 할지**가 더 중요하다.
- 화면별 문장 종류
  - 목록 한 줄 설명(`oneLiner`, 40자 이내 목표)
  - 상세 "이 프로젝트는"(`whatItIs`, 2~3문장): 처음 보는 사람이 어떤 서비스인지 이해하도록 소비자 관점으로 쓰고, 기술 용어는 쓰지 않는 것이 목표
  - "할 수 있는 일"(`features`, 3~6개): 사용자가 할 수 있는 일 위주
  - "현재 상태 · 다음 할 일"(`currentState`, `nextSteps`)
  - "기술 구성"(`techOverview`, `techStack`, `structure`): 개발자용
  - 첫 화면 Opus 인사이트: 개발 성향, 서비스 후보(pitch, 대상 사용자, 수익 방식, 다음 단계), 신규 아이디어, 정리 제안
  - UI 고정 문구: 툴팁(필터 칩, 새로고침, 다시 분석), 버튼, 빈 상태 안내, 오류 안내
- 전체 원문은 브라우저 주소창에 아래 주소를 넣으면 JSON으로 볼 수 있다.
  - http://127.0.0.1:4310/api/projects (각 프로젝트의 `summary` 필드)
  - http://127.0.0.1:4310/api/insights
- 사실 확인이 필요하면 `~/git/personal/<프로젝트명>/README.md`나 `CLAUDE.md`를 **읽기만** 한다.

## 지킬 것

- 새로고침, "인사이트 다시 분석", 실행·중지 버튼은 누르지 않는다(읽기만 하는 작업이다).

## 검토 기준

1. **가독성**
   - 한 문장이 너무 길지 않은가(대략 60자 넘는 문장 표시)
   - 주어와 서술어가 호응하는가
   - 쉼표·가운뎃점(·)·괄호가 과하지 않은가
   - 같은 단어를 반복하지 않는가
2. **쉬운 정도**
   - "이 프로젝트는"과 "할 수 있는 일"에 개발 용어, 영어 약어, 고유명사가 설명 없이 나오지 않는가
   - 예: 파이프라인, 스크리너, RS Rating, SSE, ELTD
   - 비개발자 친구가 읽고 이해할 수 있는가
3. **충분성**: "누가 쓰는지 / 무엇을 해주는지 / 왜 좋은지"가 모두 드러나는가. 읽고 나서 "그래서 이게 뭔데?"가 남지 않는가.
4. **정확성**: README나 실제 내용과 다르거나 과장한 부분이 없는가. 예전에 "싼타페 MX5" 봇을 "Mazda MX-5"로 잘못 쓴 사례가 있었다.
5. **일관성**
   - 존댓말 평서문(…합니다) 통일
   - 같은 개념에 같은 용어 사용
   - 한 줄 설명의 길이와 형식이 프로젝트마다 들쭉날쭉하지 않은가
6. **기술 구성 섹션**: 개발자에게 충분히 구체적인가, 반대로 너무 장황하지 않은가
7. **인사이트 문장**
   - 추상적인 말(예: "시너지를 낼 수 있습니다")로 끝나지 않고 구체적인가
   - 수익 방식이 현실적인 숫자와 근거를 담고 있는가
8. **UI 고정 문구**: 툴팁·버튼·안내 문구가 짧고 명확한가, 같은 기능을 부르는 이름이 화면마다 같은가

## 진행 방법

1. 31개 프로젝트 전체의 한 줄 설명과 "이 프로젝트는"을 훑고, 기준 1~5로 각각 점수를 매긴다.
2. 성격이 다른 프로젝트 8개를 골라 모든 섹션을 정밀 검토한다.
   - 웹앱, 봇, 데이터 파이프라인, CLI, 스킬·문서 저장소, git이 아닌 폴더, 커밋이 없는 저장소가 섞이도록 고른다.
3. 첫 화면 인사이트 전체와 UI 고정 문구를 검토한다.
4. 반복되는 문제 패턴을 묶어, **요약 생성 규칙(프롬프트)에 추가할 지침**으로 정리한다.

## 결과물 형식

1. **총평**: 전체 평균 점수(5점), 가장 흔한 문제 3가지
2. **프로젝트별 점수** 표(31행): `프로젝트 | 한 줄 설명 점수 | 이 프로젝트는 점수 | 주된 문제(한 줄)`
3. **정밀 검토 8개**: 섹션별로 `원문 → 문제 → 고친 문장`
4. **인사이트·UI 문구** 고칠 목록: `위치 | 원문 → 고친 문장 | 이유`
5. **생성 규칙 개선안**: 요약 프롬프트에 넣을 지침 문장 5~10개
   - 예: "고유명사·약어는 처음 나올 때 괄호로 풀어 쓴다"
   - 예: "한 문장은 50자 안팎으로 끊는다"
