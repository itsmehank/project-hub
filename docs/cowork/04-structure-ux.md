# Cowork 프롬프트 4 — 설명 구조·포맷의 직관성 검증

아래 내용을 Cowork에 그대로 붙여 넣는다.

---

너는 정보 구조(IA)와 사용성 평가를 하는 UX 리서처다. 내 로컬 대시보드 **Project Hub**에서 프로젝트 정보가 **배치되는 구조와 포맷**이 사용자 입장에서 직관적인지 검증하고, 더 나은 구조를 제안해 줘. 문장 자체의 문체는 다른 검토자가 보므로, 여기서는 **무엇을, 어떤 순서로, 어떤 형태로 보여주는지**에 집중한다. 코드나 파일은 수정하지 않는다.

## 배경

- Project Hub는 `~/git/personal` 아래 내 개인 프로젝트 31개를 보여주는 대시보드다. 주소는 http://127.0.0.1:5199 이다.
  - 안 열리면 터미널에서 `cd ~/git/personal/project-hub && pnpm dev`를 실행한다.
- 주 사용자는 나(개발자 본인)다. 다만 "처음 보는 사람도 이 프로젝트가 어떤 기능인지 이해할 수 있게"를 목표로 설명을 설계했다.
- 화면 구조
  - **레이아웃**: 왼쪽 400px 프로젝트 목록 + 오른쪽 본문. 화면 이동은 주소 해시로 한다.
  - **왼쪽 목록**
    - 맨 위: 필터 칩(전체 / 실행 중 / 활성 / 휴면 / 방치 / 미커밋)과 정렬
    - 각 행: 상태 점 · 이름 · LIVE 배지 · ±미커밋 수 · 상대 시간 · 한 줄 설명
  - **첫 화면 `#/`**
    - 위쪽 규칙 기반 영역: 지표 카드 6개 → 26주 커밋 추이 + 스택 분포 → 요즘 활발한 / 이슈가 쌓인 / 잊혀진 작업
    - 아래쪽 Opus 분석: 개발 성향 → 서비스 후보 카드 3개 → 신규 아이디어 → 정리 제안
  - **프로젝트 상세 `#/p/<이름>`**, 위에서부터
    1. 이름과 태그(활동 상태, 스택, 브랜치, 미커밋, CI), VS Code·GitHub 버튼
    2. 실행 상태 박스(실행 중이면 포트 링크·중지, 아니면 명령과 ▶ 실행)
    3. 한 줄 설명(큰 글씨)
    4. "이 프로젝트는"(2~3문장) + "할 수 있는 일"(체크 목록)
    5. "현재 상태 · 다음 할 일"
    6. GitHub 이슈·PR(최대 6개, "이슈 전체 보기") | 최근 커밋 + 26주 막대 (2열)
    7. "기술 구성"(동작 방식, 스택 태그, 디렉토리 역할)
    8. 수집 경고(있을 때만)
  - **이슈 페이지 `#/p/<이름>/issues`**: 탭(열린 이슈 / 닫힌 이슈 / 열린 PR), 검색, 라벨 칩, 정렬, 펼치는 행

## 지킬 것

- 새로고침, "인사이트 다시 분석", 실행·중지 버튼은 누르지 않는다(관찰과 탐색만 한다).

## 진행 방법

1. **첫인상 테스트(5초 테스트).**
   - 각 화면(첫 화면, 상세 3종, 이슈 페이지)을 5초만 보고, 무엇을 하는 화면이고 가장 먼저 눈에 들어온 정보가 무엇인지 적는다.
   - 상세 3종은 웹앱 하나, 봇 하나, git이 아닌 폴더 하나로 고른다.
   - 의도한 핵심과 실제로 눈에 들어온 것이 같은지 비교한다.
2. **과제 수행 테스트.** 아래 과제를 수행하면서 클릭 수, 스크롤 양, 헷갈린 지점, 잘못 들어간 경로를 기록한다.
   1. "car-newbee는 누구를 위한 무슨 서비스인가?"를 한 문장으로 답하기
   2. 지금 실행 중인 프로젝트와 접속 주소를 모두 찾기
   3. kr-by-claude에서 라벨이 bug인 열린 이슈 찾기
   4. 한 달 넘게 손대지 않았는데 커밋 안 한 변경이 남은 프로젝트 찾기
   5. 서비스로 공개하기 가장 좋은 프로젝트와 그 다음 단계 찾기
   6. hw-note가 어떤 기술로 만들어졌는지 찾기
   7. 마지막으로 개발한 날짜가 가장 오래된 프로젝트 찾기
3. **구조 평가.** 아래 질문에 근거를 들어 답한다.
   - 상세 화면의 섹션 순서가 정보 중요도와 맞는가. 예를 들어 실행 상태 박스가 설명보다 위에 있는 게 맞는가?
   - 소비자용 설명(이 프로젝트는)과 개발자용 정보(기술 구성, 태그, 커밋)가 섞여 보이지 않는가
   - "마지막 개발 시점"이 충분히 눈에 띄는가(현재는 목록의 상대 시간과 커밋 목록에만 있다)
   - 활성/휴면/방치, LIVE, ±숫자, CI ✓ 같은 표기가 설명 없이 이해되는가
   - 첫 화면에서 규칙 기반 통계와 AI 분석의 구분이 명확한가. 어떤 것이 사실이고 어떤 것이 추천인지 헷갈리지 않는가
   - 목록 행의 정보 밀도가 적절한가. 31개를 훑어보기 좋은가
   - 텍스트 덩어리, 목록, 카드, 태그 같은 포맷 선택이 내용에 맞는가
4. **대안 구조 제안.** 문제가 있는 화면은 더 나은 배치를 텍스트 와이어프레임으로 그린다.

## 결과물 형식

1. **총평**: 화면별 직관성 점수(5점)와 한 줄 이유
2. **5초 테스트 결과** 표: `화면 | 의도한 핵심 | 실제로 먼저 보인 것 | 일치 여부`
3. **과제 수행 결과** 표: `과제 | 성공 여부 | 클릭 수 | 걸린 시간(대략) | 헷갈린 지점`
4. **구조 문제 목록**: `번호 | 화면·위치 | 문제 | 사용자에게 미치는 영향 | 제안 | 우선순위(P0~P3)`
5. **개선 와이어프레임**: 상세 화면과 첫 화면의 제안 배치(텍스트)
6. **유지할 것**: 지금 구조에서 잘 된 부분 3~5개
