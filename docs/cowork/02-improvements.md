# Cowork 프롬프트 2 — 기능 개선점 발굴

아래 내용을 Cowork에 그대로 붙여 넣는다.

---

너는 개발자 도구를 많이 써 본 프로덕트 매니저다. 내가 만든 로컬 대시보드 **Project Hub**를 실제로 써 보고, 기능 측면에서 무엇을 더하거나 바꾸면 더 쓸모 있어질지 개선안을 정리해 줘. 버그 찾기(QA)는 다른 사람이 하니, 여기서는 **"이 도구가 내 목적을 얼마나 잘 돕는가"**에 집중한다. 코드나 파일은 수정하지 않는다.

## 나와 이 도구의 목적

- 나는 개인 사이드 프로젝트를 `~/git/personal` 아래에 31개 가지고 있는 개발자다. 웹앱, 텔레그램 봇, 데이터 파이프라인, CLI, 실험 폴더가 섞여 있다.
- 이 도구로 하고 싶은 일
  1. 각 프로젝트가 무엇인지, 언제 마지막으로 손댔는지, 지금 어떤 상태인지 빠르게 파악하기
  2. GitHub 이슈와 할 일 확인하기
  3. 로컬에서 띄워 볼 때 바로 실행하거나 접속하기
  4. 전체를 보고 "다음에 무엇에 시간을 쓸지", "무엇을 서비스로 공개할지", "무엇을 정리할지" 판단하기

## 서비스 설명

- 주소: http://127.0.0.1:5199
  - 안 열리면 터미널에서 `cd ~/git/personal/project-hub && pnpm dev`를 실행한다.
- 첫 화면 `#/`
  - 규칙 기반 "한눈에 보기": 지표, 26주 커밋 추이, 스택 분포, 활발한 프로젝트, 이슈가 쌓인 프로젝트, 잊혀진 미커밋 작업
  - Opus 분석: 개발 성향, 서비스 후보 3개, 신규 아이디어, 정리 제안
- 프로젝트 상세 `#/p/<이름>`
  - 실행 상태(실행·중지·로그·명령 편집), 이 프로젝트는(소비자 관점 설명), 현재 상태·다음 할 일
  - GitHub 이슈·PR·CI, 최근 커밋과 26주 막대, 기술 구성
- 이슈 페이지 `#/p/<이름>/issues`: 탭, 검색, 라벨 필터, 정렬, 본문 미리보기
- 왼쪽 목록: 필터 칩(실행 중·활성·휴면·방치·미커밋), 정렬, ⌘K 검색, ↑↓ 이동
- 새로고침: 수동이며, 바뀐 프로젝트만 Claude가 다시 요약하고 요약이 바뀌면 인사이트를 다시 분석한다.
- 설계 문서(읽기만)
  - `~/git/personal/project-hub/docs/superpowers/specs/2026-10-05-project-hub-design.md`
  - `~/git/personal/project-hub/docs/superpowers/specs/2026-10-06-insights-issues-design.md`
  - `~/git/personal/project-hub/README.md`

## 지킬 것

- 직접 실행 중인 프로세스(kr-by-claude, movie-sniper, route-guide, mx5-bot)는 중지하지 않는다.
- 실행 기능을 써 보고 싶으면 hw-note만 실행하고 끝나면 중지한다.
- "인사이트 다시 분석"(Opus)과 Shift+새로고침은 누르지 않는다. 일반 새로고침은 1회까지 허용한다.

## 진행 방법

1. **사용 시나리오로 써 보기.** 아래 상황을 실제로 해 보면서 막히는 곳, 손이 많이 가는 곳, 정보가 부족한 곳을 기록한다.
   - 월요일 아침: 지난주에 무엇을 했고, 이번 주에 무엇을 이어서 할지 정하기
   - "예전에 만든 그 영어 관련 프로젝트가 뭐였지?"를 찾아 실행해 보기
   - 이슈가 많은 프로젝트에서 오늘 처리할 이슈 3개 고르기
   - 서비스로 공개할 프로젝트 하나를 골라, 공개 전에 해야 할 일 목록 만들기
   - 오래 방치된 프로젝트를 정리할지 판단하기
2. **빈틈 찾기.** 위 목적 1~4에 비춰 아래 관점에서 빠진 기능이나 약한 기능을 찾는다.
   - 시간 흐름: 활동 추이, 최근 변화, 알림
   - 행동 연결: 화면에서 바로 할 수 있는 다음 행동
   - 우선순위 판단을 돕는 정보
   - 데이터 신선도: 수동 새로고침의 한계
   - 프로젝트 간 관계, 메모·태그 같은 개인화
3. **인사이트 품질 평가.** 첫 화면의 Opus 분석이 실제 판단에 도움이 되는지 본다.
   - 추천 근거가 납득되는가
   - 바로 행동할 수 있을 만큼 구체적인가
   - 결과를 저장하거나 추적하는 기능이 필요한가
4. **비슷한 도구와 비교.** GitHub 대시보드, Linear, Raycast, Backstage 같은 도구에서 이 맥락에 가져올 만한 아이디어가 있으면 짧게 언급한다(웹 검색 가능).

## 결과물 형식

1. **한 줄 총평**: 지금 이 도구가 목적 1~4를 각각 얼마나 잘 돕는지 5점 척도
2. **개선안 목록** 표: `번호 | 개선안 | 해결하는 불편(어느 시나리오에서) | 기대 효과 | 구현 난이도(낮/중/높) | 우선순위(P0~P3)`
   - 최소 10개, 최대 20개
   - 이미 있는 기능을 다시 제안하지 않는다.
3. **상위 3개 상세안**: 화면에서 어떻게 보이고 어떻게 동작하는지 구체적으로(간단한 텍스트 와이어프레임 포함)
4. **빼거나 줄일 것**: 쓸모가 낮거나 혼란을 주는 기능이 있으면 이유와 함께
