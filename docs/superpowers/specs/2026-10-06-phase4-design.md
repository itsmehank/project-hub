## 1. 목표

지금 허브는 "현재 상태를 보여주는 도구"다. 매번 다시 읽고 판단해야 하고, 내린 판단을 남길 곳이 없다. 4단계에서는 다음을 더한다.

1. **시간 흐름**: 한 주 동안 무엇을 했고 무엇을 이어갈지 본다(주간 리뷰).
2. **내 의도**: 프로젝트마다 내가 정한 상태(태그), 다음에 할 일(메모), 바로가기 링크를 남긴다.
3. **주의할 것**: 행동이 필요한 신호(push 안 한 커밋, 오래 열린 PR 등)와 백업이 없는 프로젝트를 구분해 보여준다.
4. **결정 기록**: AI 제안을 채택·보류·거절하고, 채택한 서비스 후보는 체크리스트로 진행을 추적한다.

## 2. 비목표 (이번 범위에서 하지 않음)

- 상태 이력(스냅샷) 저장. "지난주 대비 새로 생긴 미커밋" 같은 변화 추적은 하지 않는다.
- GitHub 이슈 생성 등 외부에 글을 쓰는 동작
- 알림(푸시, 텔레그램, 메일)
- 주간 리뷰의 AI 요약 문단(LLM 호출)
- 아이디어 제안의 유사도 매칭(제목이 바뀐 같은 아이디어를 같은 것으로 묶기)
- 폴더 이름 변경 추적(이름이 바뀌면 다른 프로젝트로 본다)
- 봇 토큰 등 `.env` 값 읽기
- upstream이 설정되지 않은 브랜치의 미푸시 커밋 감지(`ahead`는 upstream이 있을 때만 계산된다. 예: DataBatcher 두 폴더)

## 3. 기능 A — 태그·메모·바로가기 링크 (개인 데이터)

### 3.1 데이터

새 테이블. 자동 수집 데이터와 분리해 요약을 다시 만들어도 유지된다.

```sql
CREATE TABLE IF NOT EXISTS project_personal (
  name TEXT PRIMARY KEY,
  lifecycle TEXT,          -- 'focus' | 'maintain' | 'launch' | 'experiment' | 'archive' | NULL(미분류)
  note TEXT NOT NULL DEFAULT '',
  links TEXT NOT NULL DEFAULT '[]',   -- JSON: [{ "label": string, "url": string }]
  updated_at TEXT NOT NULL
);
```

| 값 | 화면 이름 | 의미 |
|---|---|---|
| `focus` | 집중 | 지금 적극적으로 개발 중 |
| `maintain` | 유지 | 완성됐고 가끔 손봄 |
| `launch` | 공개 준비 | 서비스로 공개하려고 준비 중 |
| `experiment` | 실험 | 확인용·학습용, 공개 계획 없음 |
| `archive` | 보관 | 더 이상 작업하지 않음 |
| `NULL` | 미분류 | 아직 정하지 않음(기본값) |

공유 타입:

```ts
type Lifecycle = 'focus' | 'maintain' | 'launch' | 'experiment' | 'archive';
interface PersonalLink { label: string; url: string }
interface Personal { lifecycle: Lifecycle | null; note: string; links: PersonalLink[]; updatedAt: string | null }
// Project에 personal: Personal 추가 (행이 없으면 { lifecycle: null, note: '', links: [], updatedAt: null })
```

### 3.2 검증 규칙

- `note`: 최대 500자
- `links`: 최대 5개. `label`은 1~30자. `url`은 `http:` 또는 `https:` 스킴만 허용한다(`javascript:` 등을 막는다). 텔레그램 봇은 `https://t.me/...` 형식으로 넣는다.
- 위반하면 400과 위반 항목을 응답한다.

### 3.3 API

- `GET /api/projects`와 `GET /api/projects/:name`의 각 프로젝트에 `personal` 포함
- `PUT /api/projects/:name/personal`, 본문 `{ lifecycle, note, links }`(전체 교체). 없는 프로젝트면 404. 기존 요청 가드(JSON 강제, 출처 검사)를 그대로 적용한다.

### 3.4 삭제 규칙

- 폴더가 사라져 프로젝트가 삭제되면 `project_personal` 행도 함께 삭제한다(`deleteProject`의 테이블 목록에 추가).

### 3.5 화면

- **상세 헤더**: 이름 오른쪽에 태그 선택(드롭다운)을 둔다. 한 줄 설명 아래에 메모 한 줄을 두고, 그 자리에서 편집한다(Enter 저장, Esc 취소). 바로가기 링크는 칩으로 보여주고 "링크 편집" 대화상자로 고친다. 링크 칩은 실행 여부와 관계없이 항상 보인다.
- **목록**
  - 정렬 선택 옆에 태그 선택을 둔다(전체 / 집중 / 유지 / 공개 준비 / 실험 / 미분류 / 보관).
  - 행 이름 옆에 태그 약칭 칩을 단다(미분류는 표시하지 않는다).
- **태그 선택과 필터의 관계**: 목록은 "태그 조건 → 필터 칩(실행 중·활성 등) → 검색어" 순서로 거른다. 필터 칩 숫자는 **현재 태그 조건을 적용한 뒤** 센다(`countFilters`에 태그 조건을 먼저 적용한 목록을 넘긴다).
- **보관 처리**
  - 태그 선택이 "전체"일 때는 보관 프로젝트를 뺀다. 태그 선택이 "보관"일 때만 보관 프로젝트가 보인다. 예외는 두지 않는다(실행 중인 보관 프로젝트도 "전체"에서는 숨는다. 상단 "지금 실행 중" 줄에는 그대로 나온다).
  - 목록 맨 아래에 "보관 n개 숨김 · 보기" 링크를 둔다(누르면 태그 선택을 "보관"으로 바꾼다).
  - 첫 화면 지표 카드는 보관을 빼고 센다. "전체" 카드에는 `전체 29 (+보관 2)`처럼 보관 수를 따로 표시한다.
  - 첫 화면 지표 카드를 누르면 태그 선택을 "전체"로 되돌린 뒤 해당 필터를 적용한다.
  - 주의 신호의 "잊혀진 변경"과 "백업 없음"에서 뺀다(5장).

## 4. 기능 B — 주간 리뷰

### 4.1 주의 정의

- **월요일 00:00 ~ 다음 월요일 00:00, 브라우저 로컬 시간(한국 시간)** 기준의 달력 주
- 화면에서 이번 주 / 지난주 / 2주 전을 이동한다. 2주 전을 볼 때 "직전 주 대비"를 계산하려면 3주 전 월요일까지 필요하다(최대 약 27일 전). 그래서 수집 기간을 **30일**로 둔다.
- 기존 첫 화면 26주 막대(새로고침 시각 기준 7일 묶음)는 바꾸지 않는다. 두 화면의 주 정의가 다르다는 점은 주간 리뷰 화면에 작게 적는다.

### 4.2 추가 수집 (새로고침 때)

| 항목 | 방법 | 저장 위치 |
|---|---|---|
| 기간 커밋 | `git log --since=<30일 전 00:00> --format=%H%x1f%s%x1f%cI -n 500` | `GitInfo.windowCommits?: Commit[]`, 500개에 닿으면 `GitInfo.windowTruncated?: true` |
| 최근 머지된 PR | `gh api repos/{repo}/pulls?state=closed&sort=updated&direction=desc&per_page=50`에서 `merged_at`이 30일 이내인 것 | `GitHubInfo.recentlyMergedPRs?: Item[]` (`closedAt` = `merged_at`), 응답이 50개로 꽉 찼으면 `GitHubInfo.recentlyMergedTruncated?: true` |
| 닫힌 이슈 | 기존 `recentlyClosedIssues`의 기간을 14일에서 **30일**로, `per_page`를 30에서 50으로 늘린다 | 기존 필드. 50개로 꽉 찼으면 `GitHubInfo.recentlyClosedTruncated?: true` |

- 새 필드는 선택 필드(`?`)로 둔다. 이전 새로고침으로 저장된 데이터에는 없으므로, 화면은 필드가 없으면 "다음 새로고침 후 표시됩니다"라고 안내한다.
- 잘림 표시 필드(`...Truncated`)가 true인 저장소는 주간 리뷰 합계 옆에 "일부만 집계"라고 표시한다. 개인 저장소 기준으로 상한은 충분하다고 보고 페이지를 넘기지 않는다.
- 닫힌 이슈 기간이 30일로 바뀌므로 상세 화면 GitHub 상자의 문구 "최근 14일 닫힌 이슈"를 "최근 30일 닫힌 이슈"로 고친다(`web/src/features/detail/GitHubSection.tsx`).
- 직전 주 데이터가 수집 기간보다 앞서면(예: 이 프로젝트의 수집 데이터가 오래됨) 증감률 대신 "비교 불가"를 표시한다.

### 4.3 계산 (프론트 순수 함수)

```ts
weekRange(now: Date, offset: 0 | -1 | -2): { start: Date; end: Date; label: string }  // label 예: "9/29–10/5"
weeklyReview(projects: Project[], range, prevRange): WeeklyReview
```

**같은 저장소 중복 제거**
- 저장소 키는 `githubRepo`, 없으면 `remoteUrl`이다. 둘 다 없으면 프로젝트별로 따로 본다.
- 같은 키의 프로젝트 커밋은 해시로 중복을 제거한다. 표시할 때는 대표 프로젝트(이름순 첫 번째) 아래에 "(DataBatcher-main 포함)"처럼 묶는다.
- 닫힌 이슈와 머지된 PR은 `저장소 키 + 번호`로 중복을 제거한다.

**WeeklyReview 구성**
- 합계
  - 이 주의 커밋 수와 직전 주 대비 증감(%)
  - 손댄 프로젝트 수(커밋이 1개 이상인 저장소 묶음 수)
  - 닫힌 이슈 수, 머지된 PR 수
- 프로젝트별 행(커밋 많은 순): 이름, 커밋 수 막대, 최근 커밋 제목 최대 3개, 닫힌 이슈·머지된 PR 수
- 현재 미커밋: `dirtyCount > 0`인 프로젝트 목록. "현재 시점 기준"이라고 명시한다. 이력이 없으므로 "새로 생긴"이라는 표현은 쓰지 않는다.
- 이어갈 후보(최대 5개)
  - 정렬 순서: ① 태그가 "집중"인 프로젝트 ② 이 주에 커밋이 있는 프로젝트(커밋 많은 순) ③ 메모가 있는 프로젝트
  - 보관은 제외한다.
  - 각 행에는 메모(있으면), 요약의 다음 할 일 첫 항목, "상세 보기"·"편집기에서 열기" 버튼을 둔다.
  - 체크 상태는 저장하지 않는다(결정 기록은 7장의 기능이 담당).

### 4.4 화면

- **경로**: `#/week`(이번 주), `#/week/-1`, `#/week/-2`. 상단 바 제목 옆에 "주간 리뷰" 링크를 둔다.
- **맨 위 데이터 기준 줄**: "데이터 기준: n시간 전 새로고침 [지금 새로고침]"
  - 마지막 새로고침이 12시간보다 오래됐으면 경고색으로 표시한다.
  - 마지막 새로고침이 이 주의 시작보다 이르면 "이 주의 데이터가 아직 수집되지 않았습니다"라고 안내한다.
- 그 아래에 합계 카드 → 프로젝트별 행 → 이어갈 후보 → 현재 미커밋 순서로 둔다.

## 5. 기능 C — 주의 신호와 백업 없음

### 5.1 정의 (프론트 순수 함수 `attentionSignals(projects, now)`)

**주의** (행동이 필요한 것)

| 신호 | 조건 | 표시 |
|---|---|---|
| push 안 한 커밋 | `git.ahead > 0` | `↑n push 안 함` |
| 오래 열린 PR | 열린 PR 중 `createdAt`이 30일 이상 지난 것(저장소 단위 중복 제거) | `PR n개 · 최장 n일` |
| 잊혀진 변경 | `dirtyCount > 0` 이고 활동 상태가 휴면·방치, 태그가 보관이 아님 | `±n · n일 전` |

- 기존 `portfolioStats.forgottenDirty`는 없애고 `attentionSignals`의 "잊혀진 변경"으로 대체한다(같은 계산이 두 곳에 있지 않게).

**백업 없음** (경고가 아닌 참고 목록)
- 조건: (git이고 `remoteUrl`이 없음) 또는 (git 아님)
- 제외: 태그가 보관 또는 실험인 프로젝트
- 2026-10-06 데이터 기준으로 16개가 해당한다(태그 적용 전).

### 5.2 화면

- **첫 화면**: 현황 구역의 "잊혀진 작업" 상자를 **"주의할 것"** 상자로 바꾼다. 세 신호를 종류별로 묶어 보여주고, 신호가 없으면 "지금 처리할 것이 없습니다"를 표시한다.
- 그 아래에 접힌 상태로 **"백업 없음 n개"**를 둔다. 펼치면 목록이 나오고, 각 행에 "실험으로 표시" / "보관으로 표시" 빠른 버튼을 둔다(태그를 바꾸면 목록에서 빠진다).
- **목록 행**: `ahead > 0`이면 이름 옆에 `↑n`을 경고색으로 표시한다.

## 6. 기능 D 공통 — 첫 화면 통계의 중복 집계 수정

- `portfolioStats`의 열린 이슈·PR 합계를 저장소 키 단위로 중복 제거해 센다(DataBatcher 두 폴더 같은 경우).
- 보관 프로젝트 제외 규칙(3.5)을 지표 카드에 적용한다.

## 7. 기능 E — AI 제안 결정과 체크리스트

### 7.1 결정의 정체성

AI 제안은 다시 분석할 때마다 문장이 바뀐다. 그래서 결정은 **제안 내용을 복사해 저장**하고, 다음 분석의 새 제안과는 아래 키가 같을 때만 연결한다.

| 종류 | 결정 ID | 새 제안과 연결 |
|---|---|---|
| 서비스 후보 | `candidate:<프로젝트명>` | 같은 프로젝트면 같은 결정 |
| 정리 제안 | `cleanup:<프로젝트명들을 이름순으로 정렬해 ,로 연결>` | 같은 프로젝트 묶음이면 같은 결정 |
| 아이디어 | `idea:<결정 시점 제목의 sha1 앞 12자>` | 제목이 정확히 같을 때만(유사도 매칭 없음) |

- 프로젝트 이름 정렬은 서버와 웹 모두 `localeCompare(b, 'en')`을 쓴다.
- ID 계산 함수는 `shared`에 두고 서버와 웹이 함께 쓴다.
- 서버는 PUT을 받을 때 kind별 zod 스키마로 `snapshot`을 검증하고(서비스 후보·정리 제안·아이디어 각각 InsightsSchema의 해당 항목 스키마), snapshot에서 ID를 다시 계산해 URL의 ID와 비교한다.

### 7.2 데이터

```sql
CREATE TABLE IF NOT EXISTS decisions (
  id TEXT PRIMARY KEY,
  kind TEXT NOT NULL,          -- 'candidate' | 'cleanup' | 'idea'
  status TEXT NOT NULL,        -- 'adopted' | 'held' | 'rejected'
  reason TEXT NOT NULL DEFAULT '',
  snapshot TEXT NOT NULL,      -- 결정 시점 제안 내용 전체(JSON)
  projects TEXT NOT NULL,      -- 관련 프로젝트 이름 배열(JSON)
  checklist TEXT NOT NULL DEFAULT '[]',  -- [{ "id": string, "text": string, "done": boolean }]
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

- 체크리스트 생성 규칙(하나뿐): **저장 후 상태가 `adopted`이고 kind가 `candidate`이며 체크리스트가 비어 있으면** `snapshot.nextSteps`로 만든다. 처음부터 채택이든, 보류였다가 채택으로 바꾸든 같다. 이미 항목이 있으면 건드리지 않는다. 이후 분석이 바뀌어도 그대로 둔다. 사용자는 항목을 추가·삭제·완료 표시할 수 있다(최대 20개, 항목당 200자).
- 프로젝트 폴더가 삭제돼도 결정은 지우지 않는다(여러 프로젝트에 걸칠 수 있다). 화면에서는 없는 프로젝트 이름을 회색으로 표시한다.
- 상태를 다시 바꿀 수 있다(채택 → 보류 등). 채택에서 다른 상태로 바꿔도 체크리스트는 보존한다.

### 7.3 API

- `GET /api/decisions` → `Decision[]`
- `PUT /api/decisions/:id`, 본문 `{ kind, status, reason, snapshot, projects }`
  - 생성 또는 갱신한다. ID와 kind가 7.1 규칙과 맞지 않으면 400이다.
  - 체크리스트는 7.2의 생성 규칙대로 만든다.
- `PUT /api/decisions/:id/checklist`, 본문 `{ items }` → 체크리스트 전체를 교체한다.
- `DELETE /api/decisions/:id` → 결정을 취소한다(화면에서 확인 모달을 거친다).

### 7.4 화면

- **AI 제안 카드**(서비스 후보, 정리 제안, 아이디어)
  - 카드 아래에 [채택] [보류] [거절] 버튼을 둔다.
  - 거절은 이유 입력 대화상자를 거친다(이유는 선택 입력, 최대 200자).
  - 이미 결정한 제안이면 버튼 대신 상태 배지와 "변경"을 보여준다.
- **"내 결정" 칸**(첫 화면 AI 제안 구역 맨 위)
  - 채택: 항목 이름과 체크 진행률(예: `2/5`)을 보여준다. 누르면 해당 프로젝트 상세로 이동하고, 아이디어는 내용 펼치기다.
  - 보류: 목록만 보여준다.
  - 거절: 기본으로 접어 둔다.
  - 이번 분석에 없는 결정(제안이 사라졌거나 바뀐 것)도 저장된 복사본으로 계속 보여준다.
- **프로젝트 상세**
  - 채택한 서비스 후보면 "AI 제안" 블록 안의 **서비스 후보 부분만** **"공개 체크리스트"**(진행률, 체크, 항목 추가·삭제)로 바꾼다. 같은 블록의 정리 제안과 아이디어는 그대로 둔다.
  - 채택한 정리 제안에 포함된 프로젝트면 헤더에 "정리 예정" 칩을 단다.
- **재분석 안내**: 인사이트 생성 시각 이후 태그·메모·결정이 바뀌었으면, AI 제안 구역에 "분석 이후 태그·결정이 n건 바뀌었습니다 · [다시 분석]"을 띄운다.
  - 자동 재분석은 하지 않는다(Opus 비용).
  - n은 `project_personal.updated_at`과 `decisions.updated_at`이 `insights.generatedAt`보다 늦은 행의 수다.
  - 한계: 결정을 **삭제**하면 행이 사라져 n에 잡히지 않는다. 삭제는 드문 동작이라 받아들인다.

### 7.5 인사이트 프롬프트 v3

- **입력에 추가**
  - 각 프로젝트의 태그와 메모. 보관 프로젝트는 "보관(추천 대상 아님)"으로 표시한다.
  - 결정 목록
    - 채택: 다시 제안하지 말고, 필요하면 진행을 돕는 다음 단계만 쓴다.
    - 보류: 다시 제안해도 된다.
    - 거절: 이유와 함께 넣고, 같은 제안을 반복하지 않게 한다.
- `buildInsightsPrompt(projects, now)`를 `buildInsightsPrompt(projects, decisions, now)`로 바꾸고, `InsightsManager`가 결정 목록을 DB에서 읽어 넘긴다.
- `INSIGHTS_PROMPT_VERSION = 3`. 버전이 바뀌면 해시가 달라지므로 **서버 시작 또는 다음 새로고침 때 자동으로 한 번** 다시 분석된다(Opus 1회). 따로 수동 재생성은 하지 않는다.
- 자동 재분석 해시에는 태그·결정을 넣지 않는다(7.4의 재분석 안내로 대신한다).

## 8. 공통 사항

- **DB 마이그레이션**: 새 테이블만 추가한다(`CREATE TABLE IF NOT EXISTS`). 기존 테이블은 변경하지 않는다.
- **요청 가드**: 새 PUT·DELETE 엔드포인트도 기존 가드를 통과해야 한다(JSON 강제, 출처 검사, Host 검사). DELETE는 본문이 없어도 `content-type: application/json` 헤더를 요구한다.
- **화면 문구**: 한국어로 쓰고, 기존 용어 통일 규칙(실행 중, git 아님, Claude)을 따른다.
- **LLM 호출**: 4단계 기능 자체는 LLM을 호출하지 않는다. 예외는 7.5의 프롬프트 버전 변경으로 인한 자동 재분석 1회뿐이다.

## 9. 테스트

**서버**
- `project_personal`: 저장·조회, 검증 실패(500자 초과, 링크 6개, `javascript:` URL), 프로젝트 삭제 시 함께 삭제
- `decisions`: 생성·갱신·삭제, ID 규칙 검증, 채택 시 체크리스트 자동 생성(candidate만), 프로젝트 삭제 후에도 유지
- 수집: `windowCommits`(30일 범위·500개 상한과 잘림 표시, 실제 임시 git 저장소), `recentlyMergedPRs`(`merged_at` 필터, 머지 안 된 닫힌 PR 제외, 50개 꽉 참 → 잘림 표시)
- 결정 PUT: snapshot 스키마 검증 실패 400, snapshot에서 다시 계산한 ID와 URL ID 불일치 400, 보류 → 채택 전환 시 체크리스트 생성, 이미 있는 체크리스트는 유지
- 인사이트 프롬프트 v3에 태그·메모·결정이 들어가는지
- 요청 가드가 새 엔드포인트에 적용되는지

**웹(순수 함수)**
- `weekRange`: 월요일 경계, 일요일 23:59, 연말·월말
- `weeklyReview`: 같은 저장소 커밋·PR 중복 제거, 직전 주 대비, 2주 전 보기의 직전 주 비교(3주 전 데이터), 데이터 부족 시 "비교 불가", 이어갈 후보 순서와 보관 제외
- `attentionSignals`: 세 신호 조건, 백업 없음의 보관·실험 제외
- 태그 조건을 먼저 적용한 필터 칩 숫자, 보관 제외(실행 중 포함)가 반영된 `portfolioStats`(저장소 중복 제거 포함)
- 결정 ID 생성 규칙

**브라우저**: 태그·메모·링크 편집, 주간 리뷰 주 이동, 주의할 것과 백업 없음의 빠른 태그 버튼, 채택 → 체크리스트 → 진행률, 재분석 안내

## 10. 구현 순서

각 단계는 따로 커밋하고, 각각 테스트를 먼저 쓴다. 구현 계획 문서는 범위가 커서 세 개로 나눈다: **계획 1 = A + 6장 + C**, **계획 2 = B**, **계획 3 = E**.

1. 기능 A(태그·메모·링크)와 6장(통계 중복 수정·보관 제외)
2. 기능 C(주의 신호·백업 없음). 기능 A의 태그를 사용한다.
3. 기능 B(주간 리뷰). 수집 확장이 포함되므로 새로고침 1회가 필요하다.
4. 기능 E(결정·체크리스트·프롬프트 v3). 마지막에 인사이트를 1회 다시 생성한다.
